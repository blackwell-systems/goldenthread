# Design Philosophy

goldenthread is built on a single core principle:

> **Go structs are the canonical source of truth. Everything else is derived.**

This document explains the design decisions that make this philosophy practical.

## The Golden Thread Metaphor

In traditional weaving, the golden thread is a single continuous strand that runs through the entire fabric, holding it together. If the golden thread breaks, the fabric unravels.

In software systems, the "golden thread" is **type safety and validation logic** that should run unbroken from:

```
Domain Models → API Layer → Wire Protocol → Client Validation → UI
```

Today, this thread is broken at every boundary:

```
Go Backend:        struct User { Username string }
↓ manual sync
OpenAPI:           username: { type: string, minLength: 3 }
↓ manual sync
TypeScript:        interface User { username: string }
↓ manual sync
Zod:               username: z.string().min(3)
↓ manual sync
React Form:        <input minLength={3} />
```

Every manual sync point is a place where the thread can break.

## Design Goals

### 1. Single Source of Truth

**Principle**: Write domain rules once, in Go.

**Why Go as source:**
- Backend logic is already in Go
- Go's type system is more expressive than JSON Schema
- Developers already maintain Go structs
- Go compilation catches errors early

**Alternative considered**: OpenAPI-first (schema defines Go structs)

**Rejected because**: Loses Go's type safety, forces schema language (YAML), separates domain from implementation.

### 2. Build-Time Generation

**Principle**: Generate code at build time, not runtime.

**Why build-time:**
- Zero runtime overhead
- Generated code is debuggable
- Works with static TypeScript
- Fits Go's `go generate` idiom

**Alternative considered**: Runtime reflection

**Rejected because**: Can't generate TypeScript files, performance overhead, doesn't fit Go culture.

### 3. Explicit Over Magic

**Principle**: Generated code should be obvious and readable.

**Implementation:**
- Always include source comments
- Use clear naming
- Format generated code properly
- No hidden conventions

**Example**:

```typescript
// Generated by goldenthread from models/user.go:15
// Source: Username string `gt:"required,len:3..20"`
export const UserSchema = z.object({
  username: z.string().min(3).max(20), // Clear, readable
})
```

### 4. Gradual Adoption

**Principle**: Should work alongside existing tools.

**Implementation:**
- Support `validate` tags from `validator.v10`
- Don't require framework buy-in
- Can annotate single struct
- Doesn't replace existing validation

**Example**:

```go
type User struct {
    // Existing validation continues to work
    Username string `validate:"required,min=3" gt:"export"`
    
    // Or use gt: tags directly
    Email string `gt:"email"`
}
```

## Tag Syntax Design

### Goals

1. **Familiar**: Should feel like existing Go tags
2. **Concise**: Common patterns should be short
3. **Readable**: No cryptic abbreviations
4. **Parseable**: Unambiguous grammar

### Syntax

```
gt:"rule1,rule2:value,rule3:value"
```

### Supported Rules

#### String Rules

```go
`gt:"required"`          // Field is required
`gt:"len:3..20"`         // Length range (inclusive)
`gt:"min:3"`             // Minimum length
`gt:"max:20"`            // Maximum length
`gt:"pattern:^[A-Z]+$"`  // Regex pattern
`gt:"email"`             // Email format
`gt:"url"`               // URL format
`gt:"uuid"`              // UUID format
```

#### Numeric Rules

```go
`gt:"min:0"`             // Minimum value
`gt:"max:100"`           // Maximum value
`gt:"min:0,max:100"`     // Range
```

#### Array Rules

```go
`gt:"minitems:1"`        // Minimum array length
`gt:"maxitems:10"`       // Maximum array length
`gt:"unique"`            // All items must be unique
```

### Tag Parsing Algorithm

```
1. Split on commas: ["required", "len:3..20", "email"]
2. For each part:
   a. If contains ":" → key:value rule
   b. Otherwise → boolean flag
3. Build FieldRules struct
```

## Schema IR Design

### Why an Intermediate Representation?

**Problem**: Direct Go AST → Zod code is brittle. Adding OpenAPI emitter would require duplicating AST logic.

**Solution**: Parse once into IR, emit many times.

```
Go AST ──┐
         ├─→ Schema IR ──┬─→ Zod
         │               ├─→ TypeScript
         │               └─→ OpenAPI
```

### IR Characteristics

1. **Language-agnostic**: No Go-specific concepts (pointers, interfaces)
2. **Validation-focused**: Represents rules, not implementation
3. **Composable**: Schemas can reference other schemas
4. **Serializable**: Can be saved/loaded (future: caching)

### Example Transformation

```go
// Go struct
type User struct {
    Username string `gt:"required,len:3..20"`
}

// Becomes IR
Schema{
    Name: "User",
    Fields: []Field{
        {
            Name: "Username",
            Type: FieldType{Kind: TypeString},
            Required: true,
            Rules: FieldRules{
                MinLength: ptr(3),
                MaxLength: ptr(20),
            },
        },
    },
}

// Emits to Zod
z.object({
  username: z.string().min(3).max(20),
})

// Emits to OpenAPI
username:
  type: string
  minLength: 3
  maxLength: 20
```

## Emitter Design

### Emitter Interface

```go
type Emitter interface {
    // Emit generates code from a schema
    Emit(s *schema.Schema) (string, error)
}
```

Each emitter is **independent** and **stateless**.

### Zod Emitter

**Mapping rules:**

| Go Rule | Zod Method |
|---------|------------|
| `required` | `.` (no `.optional()`) |
| `len:3..20` | `.min(3).max(20)` |
| `email` | `.email()` |
| `uuid` | `.uuid()` |
| `min:0` | `.min(0)` |
| `max:100` | `.max(100)` |
| `pattern:^[A-Z]+$` | `.regex(/^[A-Z]+$/)` |

**Type mapping:**

| Go Type | Zod Type |
|---------|----------|
| `string` | `z.string()` |
| `int`, `float64` | `z.number()` |
| `bool` | `z.boolean()` |
| `[]T` | `z.array(T)` |
| `time.Time` | `z.string().datetime()` |

### TypeScript Emitter

Generates plain TypeScript interfaces (no validation).

**Why separate?** Some projects use TypeScript without Zod. Providing plain types makes goldenthread more flexible.

### OpenAPI Emitter

Generates OpenAPI 3.0 specification.

**Design decision**: Generate complete OpenAPI document, not just components. This allows standalone API documentation.

## CLI Architecture

### Command Structure

```
goldenthread
├── generate    Generate schemas
├── check       Verify up-to-date
├── init        Create config
└── version     Print version
```

### Generate Command Flow

```
1. Parse flags (--target, --output, etc.)
2. Load goldenthread.yaml (if exists)
3. Discover Go files in source directories
4. Parse each file → Schema IR
5. For each target emitter:
   a. Generate code
   b. Write to output directory
6. Write metadata (.goldenthread/meta.json)
```

### Check Command Flow

```
1. Parse current Go files → Schema IR
2. Hash IR
3. Load metadata from previous generation
4. Compare hashes
5. Exit 0 if match, exit 1 if mismatch
```

This enables CI integration:

```yaml
# .github/workflows/ci.yml
- name: Check schemas
  run: goldenthread check ./models
```

## Extension Points

### Phase 2: DSL Support

Allow explicit schema definitions for complex validation:

```go
var PasswordResetSchema = gt.Object("PasswordReset",
    gt.Field("password", gt.String().Min(8)),
    gt.Field("confirm", gt.String()),
).Refine(func(v gt.Value) bool {
    return v["password"] == v["confirm"]
}, "Passwords must match")
```

**Implementation**: Separate DSL parser, same Schema IR output.

### Phase 3: Custom Validators

```go
type User struct {
    Email string `gt:"email,custom:corporate_email"`
}

func init() {
    gt.RegisterValidator("corporate_email", ValidateCorporateEmail)
}

func ValidateCorporateEmail(email string) bool {
    return strings.HasSuffix(email, "@corp.com")
}
```

**Challenge**: Custom Go functions can't be translated to TypeScript automatically.

**Solution**: Require users to provide TypeScript implementation:

```typescript
// custom_validators.ts
export const corporateEmail = (email: string) => email.endsWith('@corp.com')
```

Then reference in generated code:

```typescript
import { corporateEmail } from './custom_validators'

export const UserSchema = z.object({
  email: z.string().email().refine(corporateEmail, {
    message: 'Must be corporate email'
  }),
})
```

## Error Handling Strategy

### Parser Errors

Should be **helpful and actionable**:

```
Error parsing models/user.go:15
  Field: Username
  Tag: gt:"len:3..20"
  Issue: Missing 'required' tag but field type is non-pointer
  
Suggestion: Add 'required' tag or make field a pointer (*string) for optional
```

### Emitter Errors

Should indicate **what couldn't be translated**:

```
Error generating Zod schema for User
  Field: CustomType
  Issue: Type 'MyCustomType' cannot be translated to Zod
  
Suggestion: Use primitive types (string, int, bool) or nested structs
```

### CLI Errors

Should guide users to **correct usage**:

```
Error: No Go files found in ./models

Did you mean:
  goldenthread generate ./internal/models
```

## Performance Targets

### Generation Time

- **1000 schemas**: <2 seconds
- **100 schemas**: <200ms
- **10 schemas**: <50ms

Dominated by disk I/O, not computation.

### Memory Usage

- **Schema IR**: ~1KB per schema
- **1000 schemas**: ~1MB memory
- **Peak memory**: <10MB for any reasonable project

## Success Metrics

### Technical

- Zero runtime dependencies in generated code
- Generated TypeScript compiles without errors
- Generated OpenAPI validates against spec
- CI integration works reliably

### Adoption

- Solves real pain (verified by user feedback)
- Feels Go-idiomatic (no complaints about "too much magic")
- Documentation is clear (users succeed without help)
- Integration is simple (works in <5 minutes)

## Comparison with Similar Tools

### vs sqlc

**Similarities**:
- Build-time code generation
- Go-idiomatic workflow
- Clean generated code

**Differences**:
- sqlc: SQL → Go
- goldenthread: Go → TypeScript/OpenAPI

### vs gqlgen

**Similarities**:
- Schema-driven generation
- Multiple output targets
- Type-safe results

**Differences**:
- gqlgen: GraphQL schema → Go
- goldenthread: Go → multiple targets

### vs protoc

**Similarities**:
- Compiler architecture
- Cross-language type safety
- IR-based generation

**Differences**:
- protoc: .proto → multiple languages
- goldenthread: Go → frontend languages

## The Name

**goldenthread** encodes the philosophy, not just the mechanism.

Other names considered:
- `typesync`: Clear but generic
- `schemago`: Boring, utility-feel
- `contract`: Overloaded term

**goldenthread** signals:
- This is conceptual, not mechanical
- It's about continuity and connection
- It's infrastructure, not just a tool

The name positions this as a **fundamental primitive**, not just another code generator.

## Conclusion

goldenthread succeeds by:
1. **Solving a real pain** (schema drift)
2. **Fitting Go culture** (explicit codegen, not magic)
3. **Being technically sound** (clean architecture, testable)
4. **Starting simple** (tags first, DSL later)
5. **Enabling CI** (drift detection)

The architecture prioritizes **extensibility** (add emitters easily), **correctness** (schema validation), and **usability** (readable output, helpful errors).
